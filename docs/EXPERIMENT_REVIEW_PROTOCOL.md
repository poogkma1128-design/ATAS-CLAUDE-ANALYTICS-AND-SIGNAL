# Experiment and AI Responsibility Protocol

This is the operational checklist behind Handoff §5.21. It applies to signal logic, parameter sweeps,
confidence/calibration, backtests, scorer changes, and any conclusion that may later affect Telegram or real
trading. The Handoff contains project history; this file is the reusable procedure.

## 1. Two layers that must not be confused

The project uses a practical routing preference:

- GPT/Codex is the primary engineering and formal-statistics host.
- Claude is the primary challenge, omission, mechanism, and bias-review host.
- SQL/DB and deterministic code are the source of every numerical claim.
- The owner alone approves production switches, GUI/auth/secrets, and decisions that can reach a phone or
  real money.

This routing does **not** replace lifecycle independence. For each hypothesis, name these roles separately:

| Role | Responsibility | Forbidden combination in the same hypothesis |
|---|---|---|
| Proposer | states mechanism, estimand, variants, failure criteria, and planned window before results | may not give the final verdict |
| Executor/Recorder | implements/runs the deterministic pipeline and records every attempted result | may not approve its own run or report |
| Independent Reviewer | re-runs raw SQL/artifacts and checks omissions, leakage, units, regime and selection bias | may not be the proposer or executor/recorder |
| Owner | approves L3/L4 production or real-money consequences | may not delegate approval to an AI |

Using another session of the same model is only acceptable when it has not proposed or executed that
hypothesis and it independently re-runs the raw evidence. A narrative-only review is never independent.

## 2. Gate 0 — prove the measurement can work before sweeping it

The Executor/Recorder prepares the deterministic query; the Independent Reviewer re-runs it. SQL is the
evidence source, not the reviewer. Record:

- the exact feature/threshold definition, unit, null handling, and signal-time availability;
- marginal bind/pass rate and conditional bind/pass rate after earlier gates;
- breakdown by instrument × direction × session and the data-window boundaries;
- distribution/quantiles, missing rate, constant or saturated values, and impossible ranges;
- sensitivity around the current value and whether the meaning is comparable across instruments;
- query/code commit and execution timestamp.

If the feature is constant, nearly always passes/fails, has incompatible units, or changes meaning by
instrument, stop the sweep at L2. Repair or retire the measurement first.

## 3. Evidence packet required for every §5.x empirical claim

Copy this block into the experiment record or PR body. Do not omit a field; write `none` with a reason.

```text
Hypothesis / estimand:
Proposer:
Executor/Recorder:
Independent Reviewer:
Owner approval required (L1-L4):
Pre-registered variants and failure criteria:
Exact experiment_id(s):
Code / evaluator / query commit:
Data window, timezone, bar cap, instruments, sessions:
Gate 0 artifact:
Attempted variants:
Succeeded variants:
Failed variants:
Planned but not run variants:
Run but not reported variants:
Superseded or post-hoc variants (with reason):
Baseline and variant metrics: R/trade, total R, max drawdown R, fill rate, trades,
  rule × direction × instrument; calibration metrics when claiming probability:
Per-opportunity artifact version:
Uncertainty method and resampling unit:
What would falsify the conclusion:
Independent re-run result and timestamp:
Decision: provisional / rejected / owner-approved:
Runtime change, deploy, rollback:
```

Experiment IDs must be exact UUIDs. A name search or a hand-picked successful run is not complete evidence.
The packet must account for failed, running, omitted, and superseded runs as well as successful ones.

## 4. Statistical boundary

Threshold changes often change which opportunities exist. Therefore the estimand is the contrast between the
complete policy generated by variant A and the complete policy generated by variant B, not a paired test on
their intersection. Intersection-only matching drops the opportunities nearest the threshold and creates a
new selection bias.

The intended uncertainty method is block bootstrap by session × instrument, with the resampling plan frozen
before looking at the comparison. It requires stable per-opportunity artifacts containing candidate key,
variant, included/excluded plus reason, R/outcome, instrument/session, and data/evaluator version. Until
Handoff §7.2-O2 provides those artifacts, reports may describe observed aggregate differences but must say
that statistical separation is unproven.

## 5. L1-L4 objection format

Before proceeding with a problematic request, answer:

`requested action → level → what is unproven → possible impact → correct owner/role → evidence or approval required`

| Level | Meaning | Required behavior |
|---|---|---|
| L1 | numerical/reporting claim lacks reproducible source | attach deterministic query/source and limitations before answering |
| L2 | experiment or review protocol is invalid | stop at draft/experiment; repair roles, Gate 0, baseline, window, or evidence packet |
| L3 | change can affect production alerts, filters, rules, baselines, or trading decisions | do not change production; require forward evidence, independent review, rollback, and written owner approval |
| L4 | order execution, safety/telemetry removal, history destruction, or unsafe credential action | stop; owner must act after explicit impact, scope, permission, and rollback review |

Owner override cannot make a biased experiment scientifically valid. For L3/L4, record the owner, scope,
reason, evidence, confirmation, and rollback in both PR and Handoff before execution.

## 6. Nine common wrong-assignee requests

| Request | Level | Required response |
|---|---|---|
| “Claude, change and deploy the migration.” | L2 | Route implementation and three-layer verification to GPT/Codex; Claude may independently compare claims with raw logs. |
| “GPT, audit the §5.x report GPT just wrote.” | L2 | Use an independent reviewer that re-runs raw artifacts; self-review may help drafting but cannot approve. |
| “Claude, propose a feature and decide whether it wins.” | L2 | Claude may propose up to three falsifiable hypotheses; another role must execute and decide. |
| “Read this table and tell me which rule earns the most.” | L1 | Run and cite deterministic SQL/code first; do not calculate by visual reading. |
| “GPT, sweep this parameter now,” before Gate 0. | L2 | Stop and run Gate 0 first; otherwise a dead/saturated parameter wastes quota and produces false confidence. |
| “The backtest looks good; turn on Telegram.” | L3 | Refuse the production switch; require shadow/forward evidence, independent review, rollback, and written owner approval. |
| “Use confidence to filter signals.” | L3 | Refuse while v2 is `score:null` and v1 is uncalibrated; require frozen model, calibration, forward validation, and owner approval. |
| “Set `announcement_mode=manual` so signals arrive sooner.” | L3 | Refuse the evidence-gate bypass unless the owner gives recorded scope, reason, risk acceptance, and rollback. |
| “Let AI place real orders or rotate a live secret.” | L4 | Do not execute autonomously; state impact and rollback, then require the owner to perform/approve the exact action. |

## 7. Review sign-off

A report is not accepted merely because CI is green or a PR is mergeable. Acceptance requires:

- deterministic checks for engineering claims;
- a complete evidence packet for empirical claims;
- an Independent Reviewer sign-off based on a raw re-run;
- screenshot/GUI confirmation by the owner where ATAS presentation is involved;
- written owner approval before any L3/L4 production action.

If any item is missing, state `provisional` and list the missing item. Never silently promote it to fact in the
Handoff.
