## 4. กายวิภาคของแท่งที่พังหนึ่งแท่ง

|---|---:|---:|

- กริดราคาสะอาด 0.25 ทุกช่อง ไม่มีแถวซ้ำ (`max_dup = 1` ทุกแท่งทั้งสี่ตลาด)

## 5. กลไก

`AppendFootprint()` ใน `SignalBridgeIndicator.cs` ตั้ง `snapshot.Ticks` จาก **ผลรวมของ ladder เอง**
(บรรทัด 696) ⇒ ทุก payload ที่ ATAS ส่งออกมา **reconcile ในตัวเองเสมอ** ปัญหาจึงไม่ได้เกิดที่ฝั่ง
indicator แต่เกิดตอนสอง payload ของแท่งเดียวกันมาเจอกันในฐานข้อมูล:

1. ตอนสตรีมสด ATAS ส่งแท่ง — `bars` ถูก upsert, `cluster_levels` ถูก upsert ราย `(bar_id, price)`
2. กราฟรีโหลด ATAS เล่นแท่งเดิมซ้ำจาก **ประวัติที่มันเก็บเอง** ซึ่ง **บางกว่า** ที่มันเห็นตอนสด
3. แถว `bars` ถูกเขียนทับทั้งแถวด้วยค่าที่บางกว่า — แต่ `cluster_levels` เป็น upsert ราย price
   จึง **ยังเก็บแถวหนาจากรอบ live ไว้**
4. สองฝั่งจึงไม่บวกได้เท่ากันอีกต่อไป และ `reconcilesFootprint()` ปฏิเสธ footprint ทั้งแท่ง

นี่อธิบาย **ทั้ง** อัตราส่วน > 1 เสมอ **และ** แถวที่อยู่นอกช่วง `[low, high]` ของแท่ง
(MNQU6 451 แท่ง, GC 528 แท่ง) — ช่วงราคาของรอบ live กว้างกว่าของรอบส่งซ้ำ

## 6. สิ่งที่แก้ในรอบนี้

`supabase/functions/_shared/ingest.ts` — ก่อนเขียน ingest จะอ่านสิ่งที่ฐานข้อมูลมีอยู่แล้วสำหรับ
timestamp ในคำขอนั้น (`loadStoredBars`) และ **ไม่เขียนทับแท่งที่ปิดแล้วด้วย snapshot ที่บางกว่า**
แท่งที่ถูกข้ามจะไม่ถูกเขียนทั้งแถว `bars` และ `cluster_levels` ⇒ สองฝั่งแยกจากกันไม่ได้อีก

- ใช้เกณฑ์เดียว: มีแถวเดิม **และ** แถวเดิม `is_closed = true` **และ** `ticks` ที่เข้ามา < ของเดิม
- แท่งที่ยังไม่ปิดไม่เข้าเงื่อนไข (แท่งกำลังก่อตัวหดตัวได้ตามปกติ)
- แท่งที่ถูกข้ามจะ **ไม่ถูกตัดสินซ้ำ** เพราะมันถูกตัดสินไปแล้วตอนถูกเก็บสด
- อ่านตารางไม่สำเร็จ = เขียนทุกแท่งเหมือนเดิม (แท่งต้องไหลเข้าเสมอ คือสิ่งเดียวที่ห้ามพัง)
- ผลลัพธ์เพิ่มฟิลด์ `barsSuperseded`; request/response/auth ของ endpoint **ไม่เปลี่ยน** และ
  indicator อ่านแค่ status code ไม่ parse body (`HttpSender.cs:125`)

## 7. สิ่งที่ยังไม่ได้ทำ และสิ่งที่ห้ามสรุป

- **ยังไม่ deploy** — โค้ดนี้ยังไม่ถูกส่งขึ้น production ต้องรัน `supabase functions deploy ingest`
  บนเครื่องเจ้าของ. ตราบใดที่ยังไม่ deploy การส่งซ้ำยังทำลายแท่งเดิมต่อไป
- **ไม่ซ่อมข้อมูลเก่า** — 2,172 แท่งที่พังอยู่แล้วไม่ถูกแตะ การซ่อมย้อนหลังต้องรู้ว่าฝั่งไหนคือ
  ความจริง ซึ่งหลักฐานชี้ว่าคือ ladder (รอบ live) แต่ยังไม่มี independent review ของข้อสรุปนั้น
  จึงยังไม่ทำ
- **ห้ามสรุปว่าตัวเลขวิจัยเดิมจะดีขึ้นเท่าไร** — “30 โอกาส / 5 ยืนยัน” และ 14 แท่งที่ปิดด้วย
  `expired_unfired` ถูกวัดบนข้อมูลที่มีแท่งพังปนอยู่ ต้องวัดใหม่หลังมีข้อมูลสะอาดพอ ไม่ใช่
  คาดการณ์จากเอกสารนี้
- **ยังไม่มี independent review** ของรอบนี้ — Executor/Recorder: เซสชันนี้; Reviewer: ยังว่าง
- ข้อสรุปนี้ **ไม่กระทบสถานะ live**: เส้นทาง live reconcile 100% อยู่แล้ว การแก้นี้ปกป้อง
  *ประวัติ* ที่ backtest และงานวิจัยใช้ ไม่ได้เพิ่มความถี่สัญญาณของ live โดยตรง
